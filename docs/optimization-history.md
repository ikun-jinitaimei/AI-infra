# 从 baseline 到最终版本

“baseline”必须说明来源。官方原始实现、接手时已经优化的实现、同内核不同线程配置不是同一个基准。以下不将不同节点或不同计时范围的数据拼成一条严格加速曲线。

## MaiMoe：最完整的流水线优化案例

| 阶段 | 最大公开样例均值 ms | 改动与解释 |
|---|---:|---|
| 接手封装版 | 3706.430 | 后续比较起点；并非原始官方 baseline |
| 解析优化 | 1343.395 | 减少字符位置信息、AST、字符串对象 |
| 硬件 SHA | 1125.801 | 用 ARM SHA 指令完成必需摘要 |
| 局部排序、栈上事件 | 880.307 | 利用 tick 单调性，减少格式化与排序工作 |
| 缓冲与前缀复用 | 688.367 | 重用容量和同 tick 前缀，仍重新计算每个输入 |
| 向量背景、直接输出 | 656.027 | NEON 渲染并消除中间帧复制 |
| 不变量专用渲染 | 621.028 | 在成立的状态不变量下简化运算 |
| 架构编译调优 | 615.435 | TSV110 目标 |
| 最终独立全量复验 | 616.737 | 8 workers、batch 16；1 次预热 + 3 次正式测量 |

这些中间数值来自实验摘要，完整逐轮环境并未全部导出；展示工程演进，不构成每一项的独立因果消融。最终 JSON 单独保存。最大样例相对接手版本约 6.01×，其他三个样例也通过。双事件交错哈希虽使最大样例达到 605.018 ms，但另一组退化、综合得分下降，因此未采用。

## Miniclash：微基准必须接受端到端检验

同输入同种子的一组对照：标量累计 27.5275 s，4 路 SIMD 20.9690 s。另一组同轮对照：8 路 19.3977 s，16 路 15.7171 s。两组实验不同，不能把它们连接为严格的三点加速曲线。

“16 路”是用多条 128 位 NEON 指令批量处理 16 个候选，不是 512 位 ISA。固定种子下要求输出逐字节一致，完整随机任务再由官方 checker 验证。

掩码归约候选在 12 个固定单核输入上从 54.1762 s 降至 52.2270 s（约 3.60%），但三组完整 256 任务累计仅从 79.62 s 到 79.33 s，两组变慢、一组变快。没有据此替换最终版本。PGO、事件调度、重启和临时文件位置也未表现出稳定收益。

## RSM：缩短短段开销，同时守住精度与缓冲区边界

| 版本 | 公开综合加速比（相对官方参考） | 主要变化 / 状态 |
|---|---:|---|
| v15 | 4.252565× | 演进记录起点，已优化实现 |
| v16 | 4.366569× | 联合矩归约；当时通过，随后发现相关容量路径存在缺陷，不推荐 |
| v17 | 4.808745× | 多段输入组批、连续分配；不使用上述双矩容量路径 |
| v18 | 无有效成绩 | 合并改动后 57/58，补齐后的临时缓冲容量不足 |
| v19 | 4.946081× | 修正容量并联合计算短段 |
| v20 | 5.227821× | 允许变长短段共同计算 |
| v21 | 5.256323× | 更宽分组与运算复用 |
| v23 | 5.303054× | 向量搬移与权重展开；最终已验证版本 |
| v25 | 未测 | 工作量估计下的连续划分候选，不作为确认收益 |

v15 到 v23 的综合指标提高约 24.70%。这是公开用例的综合加速指标变化，不表示每个用例都降低相同百分比的耗时。每次容量判断必须覆盖对齐/归约补齐后的形状，而非只有真实元素数。v16 的一次通过不能覆盖后来发现的问题。

## 其他案例的可比性

- Accelerate：同轮原版 4.6078 s，8 查询 libm 2.2900 s、8 查询向量多项式 1.6863 s。最终另一次正式测量取三个新进程最慢值 1.178475 s；两者不相除作为严格加速比。
- Blackhole：最终完整四例均通过；历史短迭代、不同节点及不同布局的数据不混成 baseline-to-final 倍数。共享窗口、插值复用与 Fourier 重组的机制见案例页。
- Mahjx：最终两局 414.530433 s；不同线程数、节点和前缀片段测试不合并为端到端倍数。最后未测追加版保留在本地，不混入公开已测补丁。
- Rune：展示调度策略和合法性/得分验证，不将其包装为 CPU 指令级加速。
- LLM Serving：Stage1 的可写 HOME/TMP 修复是运行条件修复；没有对照证据证明它本身带来吞吐提升。
